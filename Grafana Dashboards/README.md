# Grafana Dashboards

Каталог описывает рекомендуемые дашборды для PostgreSQL-базы бота
`Kate_fitness`. Готовые запросы лежат в [sql/metrics.sql](sql/metrics.sql),
а JSON для импорта — в `dashboards/`:

- `overview.json` — финансы и расписание;
- `prepaid-packages.json` — отдельная аналитика по пакетам предоплаты.

Оба JSON используют заданный UID PostgreSQL datasource `bfxxeavvzooaoc`.
В них нет адреса БД, пользователя, пароля и других секретов.

## Что есть в данных

Актуальная модель — результат миграции `0002_site_model`:

| Сущность | Роль в аналитике |
| --- | --- |
| `main.schedule` | факт запланированной тренировки: дата/время, цена, аренда, тип, персональный или групповой формат |
| `main.schedule_participant` | состав групповой тренировки; источник числа участников |
| `main.accounting` | проданные пакеты предоплаты, их стоимость, размер и статус закрытия |
| `main.client` | клиент, дата добавления и признак неактивности |
| `main.trains` | справочник типов тренировок и аренда на занятие |
| `main.price` | история цены клиента, пригодна для проверки и развития аналитики цен |

Важное различие: `schedule.price` — выручка по проведённым/внесённым в
расписание занятиям; `accounting.summ` — деньги, полученные при продаже
пакетов. Эти показатели нельзя складывать: это разные моменты признания
одной продажи. Текущий отчёт бота считает прибыль как
`sum(schedule.price) - sum(schedule.rent_debt)`.

## Переменные Grafana

Во всех дашбордах стоит завести общие переменные:

- `type_train` — запрос по `main.trains.type_train`, с вариантом `All`;
- `format` — `personal` / `group` / `all`, соответствует `schedule.is_group`;
- `client` — необязательный фильтр по клиенту; для групп учитывается
  `schedule_participant`;
- стандартный диапазон времени Grafana; для финансов — месяц, для расписания
  — неделя или 30 дней.

Не выводить в заголовках и легендах номера телефонов: достаточно имени клиента
и внутреннего `id`.

## 1. Финансы

Цель — видеть объём работы, маржу и продажи пакетов.

| Панель | Визуализация | Метрика / расчёт |
| --- | --- | --- |
| Выручка по занятиям | Stat + time series | `SUM(schedule.price)` за период |
| Расходы на аренду | Stat + time series | `SUM(schedule.rent_debt)` |
| Валовая прибыль | Stat + time series | `SUM(price - rent_debt)` |
| Маржинальность | Gauge | `profit / revenue * 100`; если выручки нет — `NULL` |
| Выручка и прибыль по типам | Bar chart | те же суммы с разрезом `trains.type_train` |
| Продажи пакетов | Time series | `SUM(accounting.summ)` по `created_at` |
| Средний чек пакета | Stat | `AVG(accounting.summ)` |
| Плановая стоимость незакрытых пакетов | Stat | `SUM((count_train - used) * price_per_train)`; не является остатком денег на счёте |

## 2. Нагрузка и расписание

Цель — понять занятость тренера и структуру тренировок.

| Панель | Визуализация | Метрика / расчёт |
| --- | --- | --- |
| Количество тренировок по дням | Time series | `COUNT(schedule.id)` |
| Персональные против групповых | Stacked bar | число записей с `is_group = false/true` |
| Участники групп | Time series + Stat | `COUNT(schedule_participant.client_id)` только для групп |
| Средний размер группы | Stat | участники / число групповых занятий |
| Нагрузка по часам и дням недели | Heatmap | число занятий в разрезе `EXTRACT(DOW FROM date)` и `time` |
| Топ типов тренировок | Bar chart | число занятий и выручка по `type_train` |
| Ближайшие занятия | Table | дата, время, формат, тип, цена, число участников |

Текущая таблица не хранит отмены и фактическую отметку проведения. Поэтому
все эти показатели пока отражают внесённое расписание, а не подтверждённое
посещение.

## 3. Клиенты и удержание

Цель — следить за активной базой и возвращаемостью.

| Панель | Визуализация | Метрика / расчёт |
| --- | --- | --- |
| Всего / активных / неактивных клиентов | Stat | `COUNT(client.id)`, с фильтром `inactive` |
| Новые клиенты | Time series | `COUNT(*)` по `client.add_time` |
| Клиенты с тренировками | Stat | уникальные клиенты из персональных записей и участников групп |
| Активные за 30 дней | Stat | уникальные клиенты с занятием в последние 30 дней |
| Клиенты без занятий 30/60/90 дней | Table + Stat | дата последней тренировки по каждому клиенту |
| Топ клиентов по занятиям | Table | клиент, число тренировок, дата последней |
| Когорты по месяцу регистрации | Cohort/table | месяц `add_time` × месяц первой/последующей тренировки |

Для точной retention-воронки потребуется правило, что считать оттоком
(например, 60 дней без занятия); это бизнес-настройка, а не свойство БД.

## 4. Предоплаты и риск списания

Цель — вовремя видеть открытые пакеты и их использование.

| Панель | Визуализация | Метрика / расчёт |
| --- | --- | --- |
| Активные пакеты | Stat | `COUNT(accounting.id WHERE is_complete = false)` |
| Осталось занятий | Stat / Bar | `SUM(count_train - COUNT(schedule.accounting_id))` по открытому пакету |
| Использование пакетов | Bar | `(used / count_train) * 100` по типу / клиенту |
| Почти исчерпанные пакеты | Table | открытые пакеты, где осталось 1–2 занятия |
| Просроченно открытые пакеты | Table | открытые пакеты старше выбранного порога, например 90 дней |
| Закрытые пакеты | Time series | число пакетов с `is_complete = true`; дату закрытия сейчас определить нельзя |

Списание в проекте связывается через `schedule.accounting_id`; только такие
персональные тренировки учитываются как использованные в пакете. Групповые
занятия с пакетами сейчас не связаны.

`prepaid-packages.json` содержит фильтр по типу тренировки: можно отдельно
выбрать «Дом», «Реформер» или другой тип из справочника `main.trains`. Помимо
общих остатков, в нём есть возраст пакета, процент использования, плановая
стоимость неиспользованных занятий, пакеты с малым остатком и давно открытые
пакеты. Пороги для последних двух панелей переключаются вверху дашборда.

## Рекомендуемый порядок внедрения

1. Подключить PostgreSQL datasource к базе `Kate_fitness` с read-only ролью и
   доступом только к схеме `main`.
2. Собрать «Финансы» и «Нагрузка» — для них достаточно текущих данных.
3. Добавить «Клиенты» и «Предоплаты», предварительно согласовав пороги
   неактивности и просрочки.
4. После проверки бизнес-терминов экспортировать согласованные дашборды из
   Grafana в JSON и хранить их в этом каталоге рядом с SQL.

## Ограничения и следующие улучшения модели

Для полноценной управленческой аналитики не хватает статуса занятия
(`planned`/`completed`/`cancelled`), даты отмены и причины, факта оплаты
разовой тренировки, а также `completed_at` для пакета. Их отсутствие не мешает
базовым панелям, но не позволяет корректно считать no-show, отмены, cashflow
и длительность жизни пакета. Метрики здоровья сервиса (ошибки бота/API,
доступность PostgreSQL, задержка запросов) также потребуют отдельного
Prometheus/Loki-инструментирования: в прикладных таблицах их нет.
