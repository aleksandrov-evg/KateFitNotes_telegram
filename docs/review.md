# Ревью проекта KateFitNotes

Персональный Telegram-бот учёта клиентов, тренировок, предоплат и прибыли. Документ фиксирует текущее состояние кода, найденные проблемы и список улучшений с учётом двух целей:

1. подготовка общей бизнес-логики к будущему веб-сайту;
2. возможность писать устойчивые автотесты.

Дата ревью: 22.08.2026.

---

## 1. Краткое резюме

Сейчас это **монолитный Telegram-бот**: UI, сценарии, состояние и SQL живут рядом. Бизнес-правила нельзя вызвать отдельно от `telebot`, схему БД нельзя воспроизвести из репозитория, тесты сломаны.

Для сайта и автотестов это главный блокер. Пока логика «добавить клиента / занятие / предоплату / отчёт» не вынесена из хендлеров Telegram, веб-приложение либо продублирует правила, либо будет невозможно нормально покрыть тестами.

Рекомендуемый вектор: **сначала слой домена и репозиторий + миграции + тесты**, затем API, затем сайт. Бот оставить тонким адаптером к Telegram.

## 2. Текущая архитектура

```
Telegram  →  bot.py (меню, FSM, валидация, SQL-вызовы, сообщения)
                 ↓
              sql.py (f-строки, новое соединение на запрос)
                 ↓
           PostgreSQL 14, схема main (живёт только в БД)
```

| Файл | Роль | Замечания |
|------|------|-----------|
| `bot.py` (~577 строк) | точка входа, хендлеры, клавиатуры, глобальное состояние | вся прикладная логика |
| `sql.py` | все запросы к PostgreSQL | нет пула, нет параметризации, соединения не закрываются |
| `src/Kate_Fit_Notes/process_class.py` | `CurrentData` — состояние оплаты | дублирует поля словаря `current_data` |
| `src/Kate_Fit_Notes/pipelines.py` | пустой | не использовать |
| `main.py` | заглушка PyCharm | бот не использует |
| `test.py` | черновые pytest | синтаксически невалиден, в `.gitignore` |
| `config.ini` | токен и SQL host/port/database | не в git |
| `docker-compose.yml` | Postgres, тестовый Postgres, pgAdmin, бот | опечатки env, нет healthcheck |

Сценарии, которые уже есть и которые сайт почти наверняка повторит:

- клиенты (телефон как идентификатор);
- персональные и групповые занятия;
- предоплата пакета и списание по занятиям;
- помесячный отчёт `income = sum(price) - sum(rent_debt)`.

## 3. Что мешает сайту и тестам

### 3.1. Нет границы между UI и доменом

Правила размазаны по `bot.py`:

- нормализация телефона — в `validate_phone`;
- разбор «сумма + количество» — в `get_text_messages`;
- выбор цены с учётом предоплаты — в `input_train_price`;
- закрытие аванса на последней тренировке — в `confirm_add` + `insert_in_schedule`;
- отчёт — прямой вызов SQL из хендлера.

Сайт не сможет переиспользовать это без копирования. Юнит-тест не сможет проверить «закрыть предоплату», не поднимая Telegram.

**Цель рефакторинга:** функции/сервисы вида `create_client`, `book_personal_session`, `add_prepaid`, `monthly_report`, которые принимают обычные данные и не знают про `message` / `call`.

### 3.2. Два параллельных контура состояния

- `current_data` — `dict` + `current_data_clear()` для расписания;
- `current_data_new` — экземпляр `CurrentData` для оплаты.

Поля почти одинаковые. После выбора типа персональной тренировки `process` обнуляется (`current_data['process'] = None`), чтобы дата/время обрабатывались в другой ветке `callback_inline`. Это хрупко и почти не тестируется: шаг зависит от глобальных переменных и порядка callback.

Для сайта понадобится явное состояние сессии (или stateless API). Для тестов — возможность подставить состояние без Telegram.

### 3.3. Глобальное однопользовательское состояние

`current_data`, `allow_add_client`, `dict_date` — модульные глобальные переменные, без `chat_id`. Бот рассчитан на одного пользователя. Для сайта это неприемлемо: нужны пользователь, сессия, права.

Даже до сайта это ломает тесты: два теста подряд влияют друг на друга.

### 3.4. Схема БД не версионируется

Миграций нет. Структура таблиц живёт в работающей Postgres. Нет `CREATE TABLE`, нет seed типов тренировок.

Следствия:

- тестовую БД нельзя поднять «с нуля» из репозитория;
- сайт и бот легко разъедутся по полям;
- изменение `client` = телефон или формата `client_list` нельзя сделать контролируемо.

### 3.5. Слой данных — не репозиторий

`sql.py`:

- собирает SQL через f-строки (инъекции, ломается на кавычках в имени);
- `execute_query` открывает соединение и не закрывает его;
- `autocommit=True`, при этом `insert_in_schedule` шлёт `BEGIN; ... COMMIT;` одной строкой;
- контракт ответа `['SELECT', '<n>', list[dict]]` неудобен: вызывающий код пишет `result[1]`, `result[2]`;
- `INSERT`/`UPDATE` возвращают `None` — нельзя проверить id без `RETURNING` и разбора;
- `os.system("docker inspect ...")` возвращает код выхода, а не IP.

Такой слой нельзя подменить фейком. Для сайта и тестов нужен интерфейс репозитория и параметризованные запросы.

### 3.6. Идентификаторы и модель данных заточены под бота

- клиент идентифицируется **телефоном** (10 цифр), не surrogate key;
- групповые клиенты пишутся строкой `{id1,id2,...}` в `client_list`, поле `client = -1`;
- `callback_data` часто — **индекс в текущем списке**, не id из БД;
- цена при `train_price is None` подставляется как вложенный `SELECT` внутрь `INSERT`.

Сайт с нормальными URL `/clients/123`, фильтрами и формами на такой модели будет неудобен. Тесты будут зависеть от порядка строк в выборке.

## 4. Найденные дефекты и риски

Ниже — конкретные проблемы, которые стоит закрыть по пути рефакторинга (часть из них уже ломает прод-сценарии).

### Критичные

1. **SQL-инъекции и хрупкий SQL.** Имена, даты, списки клиентов подставляются в f-строки. Апостроф в фамилии ломает `INSERT`.
2. **Голый `except:`** в `insert_data` и в добавлении предоплаты: ошибка глотается, пользователь видит «Ошибка», в логах нет traceback.
3. **Баг добавления клиента.** Если `validate_phone` вернул `0` (невалидный номер), условие `if not phone_number` показывает «Такой клиент уже существует», а не ошибку формата.
4. **Соединения не закрываются.** Утечка соединений к Postgres при любом трафике, тем более с сайта.
5. **`test.py` не запускается.** `host=,` / `port=,` — синтаксическая ошибка. Файл в `.gitignore`, в Docker копируется, но в git его может не быть.
6. **Dockerfile:** `CMD ["python3","-m", "bot.py"]` некорректно для запуска модуля (нужно `python3 bot.py` или `python3 -m bot`).
7. **Compose:** `POSTGRESS_DB` вместо `POSTGRES_DB` — имя БД из env не применяется, создаётся дефолтная.

### Логика сценариев

8. Два хендлера с одним декоратором `@bot.message_handler(commands=['show_time'])`: пустой `confirm_add` и `show_available_time`. Первый перекрывает второй, если бы команды вызывались как Telegram-команды; функции ещё и вызываются напрямую — путаница имён.
9. В `show_available_time` в сообщение уходит `current_data["operation"]` вместо даты.
10. `confirm_add` всегда собирает текст из `client_multi[...][1]`. Если список `None` — падение.
11. После выбора типа персональной тренировки `process = None`. Любой параллельный callback с тем же `operation` может попасть не в ту ветку.
12. Несколько незакрытых авансов: запись блокируется сообщением, но `start()` вызывается сразу, состояние может остаться грязным.
13. `get_count_prepaid_train` джойнит accounting и schedule по клиенту без привязки к конкретной строке аванса — легко посчитать «чужие» занятия.
14. Деление `summ / count_train` без проверки на ноль.
15. `insert_balance` формирует `VALUES` как один кортеж в кавычках — функция фактически мертвая.
16. `'now()'` в INSERT accounting — это строка, не функция `now()`.

### Инфраструктура и поставка

17. `requirements.txt` — freeze со служебными пакетами pytest, неиспользуемый `keyboa`, старые `certifi`/`urllib3`.
18. Нет `.env.example`, конфиг размазан между `config.ini` и `TG_ACCOUNT`/`TG_PASS`.
19. Нет healthcheck у Postgres, бот может стартовать раньше БД.
20. `main.py` и пустой `pipelines.py` засоряют репозиторий.
21. В git попадают `.idea/*`.
22. Нет логирования через `logging`: только `print`.
23. Нет авторизации бота (whitelist `chat_id`): любой, кто знает username бота, работает с прод-данными.

## 5. Целевая архитектура (бот + сайт + тесты)

Один бэкенд, несколько адаптеров.

```
                    ┌─────────────┐
  Telegram bot  ───►│  HTTP API   │◄───  Web (React/Vue/etc.)
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  application │  use-cases: клиенты, слоты,
                    │    layer     │  предоплаты, отчёты
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │ repositories │  SQLAlchemy / psycopg + модели
                    └──────┬──────┘
                           │
                    ┌──────▼──────┐
                    │  PostgreSQL  │  миграции Alembic
                    └─────────────┘
```

Практичный минимум без лишней «энтерпрайзности»:

| Слой | Ответственность | Пример |
|------|-----------------|--------|
| `domain` / `models` | сущности и инварианты | Client, Session, PrepaidPackage |
| `services` | сценарии | `BookingService.book_personal(...)` |
| `repositories` | доступ к БД | `ClientRepository.get_by_phone` |
| `bot` | клавиатуры и маппинг update → service | тонкие хендлеры |
| `api` | REST/JSON для сайта | FastAPI |
| `web` | UI сайта | позже, отдельно |

Бот и сайт не должны содержать SQL и правила предоплаты.

## 7. Стратегия автотестов

Тесты нельзя надёжно писать «поверх» текущего `bot.py`: хендлеры требуют объекты Telegram, глобальное состояние и живую БД с неизвестной схемой.

### 7.1. Пирамида

```
        E2E бота (мало)
       /                \
  API / бот интеграция   \
 /                        \
сервисы + БД (testcontainers / docker pg_db_test)
\
 чистые юниты: валидация, расчёт слотов, списание предоплаты
```

### 7.2. Что покрывать в первую очередь

**Юнит-тесты (без I/O)**

- телефон: `+7` / `7` / `8` / мусор / короткий номер;
- ввод цены: только цифры;
- ввод предоплаты: `"1000 10"`, лишние пробелы, ноль тренировок;
- свободные слоты: рабочие часы минус занятые;
- навигация недели: prev / current / next;
- правило «последняя предоплаченная тренировка → is_complete».

**Интеграционные тесты сервисов + Postgres**

Поднимать `pg_db_test` (порт 5433) **по миграциям**, не копируя прод.

- создать клиента, повтор того же телефона — ошибка уникальности;
- персональная запись занимает слот, повтор на ту же дату/время — отказ;
- групповая запись: состав участников читается обратно;
- предоплата: N занятий списываются, N+1-е уже не из пакета;
- два открытых пакета — отказ или явное правило (сейчас бот блокирует);
- отчёт за месяц: `sum(price) - sum(rent_debt)`.

**Контракт API (когда появится)**

- схема ответа клиентов/записей;
- 401 без токена;
- 409 на занятый слот.

**Бот (тонкий слой)**

- мок `TeleBot.send_message` / callback: по тексту кнопки вызывается нужный use-case;
- не дублировать бизнес-проверки в этих тестах.

Не делать E2E через реальный Telegram, пока нет ядра: это дорого и нестабильно.

### 7.3. Что нужно в репозитории для тестов

- `tests/` вместо одного `test.py`;
- фикстура соединения/сессии с откатом транзакции или truncate;
- фабрики клиентов и типов тренировок;
- запрет на попадание тестов в прод-БД (отдельный `DATABASE_URL`);
- pytest в CI. Контейнер `db_pg_test` уже заведён — его имеет смысл оставить, но наполнить миграциями.

Текущий `test_search_client` с `assert int(query[1]) != 0` зависит от данных в БД и непригоден как образец.

### 7.4. Тестируемость хендлеров — условие рефакторинга

Чтобы тестировать бота без живого polling:

- не вызывать `bot.infinity_polling()` при `import bot`;
- собирать клавиатуры и тексты функциями, возвращающими структуры, а не только отправляющими в Telegram;
- сервисы принимать как зависимость (или модуль), а не ходить в `sql` напрямую.

Иначе каждый тест будет слать сообщения или падать на токене.

## 8. План внедрения (чтобы не переписать всё сразу)

Делать вертикальными срезами, каждый срез заканчивается тестами.

### Этап A — фундамент (1–2 итерации)

1. Конфиг из env, починить Docker CMD и `POSTGRES_DB`.
2. Миграция «как есть» (снимок текущей схемы), без смены модели.
3. Параметризовать SQL, закрывать соединения.
4. Чистые функции валидации + юнит-тесты.
5. Починить баги телефона, даты, `except`, `'now()'`.

После этапа бот внешне тот же, но его уже можно страховать тестами.

### Этап B — сервисы

1. `BookingService` / `ClientService` / `PrepaidService` / `ReportService`.
2. `bot.py` только вызывает сервисы.
3. Один объект состояния сценария, ключ — `chat_id`.
4. Интеграционные тесты на тестовой БД.

### Этап C — модель под сайт

1. PK клиента, нормальные участники занятия, `accounting_id` на записи.
2. Миграция данных, бот продолжает работать.
3. Уникальность слота.

### Этап D — API и сайт

1. FastAPI с теми же сервисами.
2. Авторизация.
3. Сайт как клиент API (календарь, клиенты, отчёты).
4. Контрактные тесты API.

Не начинать сайт с чтения тех же таблиц напрямую: правила предоплаты снова разъедутся.

---

## 9. Что сознательно не делать в первом заходе

- не внедрять полноценный FSM-фреймворк Telegram, пока сценарии не вынесены в сервисы;
- не параметризовать «все запросы мира» отдельным PR без выноса сервисов — лучше вместе с репозиторием;
- не менять смысл `client` = телефон и формат `client_list` без миграции и этапа C;
- не писать multi-user продукт в боте до привязки состояния к `chat_id`;
- не тащить фронт, пока нет API и тестов ядра.

## 10. Приоритетный backlog (кратко)

**Сначала (тесты станут возможны):**

1. Чистые функции + юнит-тесты валидации и слотов.
2. Миграции схемы as-is.
3. Репозиторий с параметрами и закрытием соединений.
4. Сервисный слой поверх репозитория + интеграционные тесты на `pg_db_test`.
5. Бот как адаптер; состояние по `chat_id`.

**Потом (сайт не скопирует хаос):**

6. Нормальные id клиента и состав группы.
7. Явная связь занятия с предоплатой.
8. REST API + авторизация.
9. Сайт на API.

**Параллельно по мере касания файлов:**

- починить баги из раздела 4;
- logging вместо `print` и голого `except`;
- Docker/compose/requirements;
- CI: pytest.

Без пунктов 1–5 новый сайт либо повторит текущую логику в другом языке/фреймворке, либо будет писаться без автотестов на главные деньги-сценарии (запись и предоплата).
